第八课 · Agent 系统

Agent 与工具调用
让模型采取行动

前面七课，模型只能"说话"——接收文本、输出文本。但真正有用的 AI 助手需要"动手"：查数据库、调 API、写文件、执行代码。这节课我们学习如何让大模型从"聊天机器人"进化为"能做事的 Agent"。

0 从聊天到行动

大模型本质上只会做一件事：给定输入文本，输出下一段文本。但如果我们允许模型在输出中"调用工具"——并把工具的结果反馈给它——它就变成了一个能与世界交互的 Agent（智能体）。

💬 Agent 对话示例：查询天气

用户
明天北京天气怎么样？需要带伞吗？
模型 → 调用工具
get_weather(city="北京", date="2025-01-16")
工具返回结果
{"temp": "2°C ~ -5°C", "weather": "小雪", "precipitation": 0.85}
模型
明天北京预报有小雪，气温 -5°C 到 2°C，降水概率 85%。建议带伞，同时注意保暖——围巾和厚外套都穿上吧！

关键观察：模型不是直接"编造"天气信息，而是决定需要什么信息 → 调用对应工具 → 基于真实数据回答。这从根本上解决了大模型"幻觉"的问题——它不需要记住天气，只需要知道"该问谁"。

1 Function Calling：模型如何调用工具

Function Calling（函数调用）的实现原理其实很简单：在 prompt 中告诉模型有哪些工具可用，然后训练模型在需要时输出特定格式的"调用指令"。

# 1. 给模型描述可用工具（作为 system prompt 的一部分）： tools = [ { "name": "get_weather", "description": "查询指定城市和日期的天气预报", "parameters": { "city": {"type": "string", "description": "城市名"}, "date": {"type": "string", "description": "日期 YYYY-MM-DD"} } }, { "name": "search_web", "description": "搜索互联网获取最新信息", "parameters": {"query": {"type": "string"}} } ] # 2. 模型看到用户问题后，生成工具调用（特殊格式的文本）： 模型输出: {"tool_call": "get_weather", "arguments": {"city": "北京", "date": "2025-01-16"}} # 3. 系统执行工具，把结果返回给模型： 系统注入: {"tool_result": {"temp": "2°C ~ -5°C", ...}} # 4. 模型基于工具结果生成最终回答 # 本质：模型学会了在需要时输出"JSON 格式的工具调用" # 而不是直接回答用户。这是训练出来的能力。
💡

核心洞见：Function Calling 不需要模型架构的任何改变——模型还是在做 Next-Token Prediction。只不过它被训练为"在某些情况下，输出的下一个 token 序列是一个 JSON 格式的工具调用"。工具调用只是一种特殊的输出格式，和输出诗歌、代码没有本质区别。

常见的工具类型：

🔍
搜索
查询互联网
获取最新信息
💻
代码执行
运行 Python
做计算/画图
📄
文件操作
读/写/编辑
本地文件
🗃️
数据库
查询 SQL
获取结构化数据
🌐
API 调用
调用外部服务
发邮件/下单
🖼️
图像生成
调用 DALL-E
生成图片

2 Agent Loop：思考-行动-观察循环

一个工具调用可能不够——复杂任务需要多步推理和多次工具调用。这就是 Agent Loop（代理循环）：模型不断地"思考→行动→观察→思考"直到任务完成。

🔄 Agent 循环（ReAct 模式）

🤔 Thought：分析当前情况，决定下一步
↓
🔧 Action：调用工具 / 执行操作
↓
👁️ Observation：获取工具返回的结果
↓
✅ Answer：够了就回答 / 不够就继续循环
↺ 重复直到任务完成（或达到最大步数）

💬 多步 Agent 示例：帮用户规划旅行

用户
帮我查一下下周末上海到杭州的高铁，然后推荐一家西湖附近的酒店
Thought
用户需要两个信息：1) 高铁车次 2) 酒店推荐。我先查高铁。
Action
search_trains(from="上海", to="杭州", date="2025-01-18")
Observation
[{"train":"G7501","depart":"08:15","arrive":"09:12","price":73}, {"train":"G7553","depart":"10:30","arrive":"11:25","price":73}, ...]
Thought
高铁信息拿到了。现在查西湖附近的酒店。
Action
search_hotels(location="杭州西湖", checkin="2025-01-18", checkout="2025-01-19")
Observation
[{"name":"西湖国宾馆","price":1280,"rating":4.9}, {"name":"湖畔花园酒店","price":680,"rating":4.7}, ...]
Answer
帮你查好了！🚄 高铁推荐：G7501 次，08:15 上海出发，09:12 到杭州，二等座 73 元。🏨 酒店推荐：湖畔花园酒店，距西湖步行 5 分钟，680 元/晚，评分 4.7。性价比很高！需要我帮你预订吗？
🧠

Agent 的"智能"来自哪里？Agent 的能力 = 模型的推理能力 + 工具的执行能力。模型负责"做决策"（调什么工具、传什么参数、怎么整合结果），工具负责"做执行"（真正去查数据、调 API）。模型本身不会查高铁——但它知道"该调用 search_trains"并且能正确填入参数。这种"知道何时做什么"的判断力来自训练。

3 System Prompt：定义 Agent 的"灵魂"

Agent 的行为很大程度上由 System Prompt 决定——它告诉模型"你是谁、能做什么、该怎么做"。

# 一个典型的 Agent System Prompt： system_prompt = """ 你是一个智能助手，可以使用以下工具来帮助用户： ## 可用工具 1. search_web(query) - 搜索互联网 2. run_python(code) - 执行 Python 代码 3. read_file(path) - 读取文件内容 4. write_file(path, content) - 写入文件 ## 行为准则 - 优先使用工具获取真实信息，不要编造 - 不确定时先搜索再回答 - 涉及计算时使用 run_python，不要心算 - 每次只调用一个工具，等待结果后再决定下一步 - 如果工具调用失败，尝试换一种方式或告知用户 ## 输出格式 需要调用工具时，输出： {"tool": "工具名", "args": {"参数": "值"}} 不需要工具时，直接回答用户。 """

好的 System Prompt 的要素：

  • 角色定义——明确模型的身份和职责边界
  • 工具描述——每个工具的功能、参数、返回值
  • 行为准则——什么时候该调工具、什么时候直接回答
  • 输出格式——工具调用的 JSON 格式，模型需要严格遵守
  • 错误处理——工具失败时该怎么办

4 RAG：检索增强生成

RAG（Retrieval-Augmented Generation）是 Agent 最常用的模式之一：先从知识库中检索相关信息，再让模型基于检索结果生成回答。它本质上就是"先查资料再回答"。

# RAG 的工作流程： # 1. 用户提问 query = "我们公司的年假政策是什么？" # 2. 把问题转换为向量（Embedding） query_vector = embed(query) # [0.12, -0.34, 0.78, ...] # 3. 在向量数据库中搜索最相关的文档片段 results = vector_db.search(query_vector, top_k=3) # → ["员工手册第5章：年假政策...", "HR FAQ...", ...] # 4. 把检索结果作为上下文，让模型基于此回答 prompt = f"""基于以下参考信息回答用户问题： 参考信息： {results} 用户问题：{query} 请基于参考信息回答，如果信息不足请说明。""" answer = model.generate(prompt) # → "根据公司员工手册，入职满一年后享有5天年假..."

RAG 的优势：

  • 减少幻觉——模型的回答基于真实检索到的文档
  • 知识可更新——更新文档库即可，不需要重新训练模型
  • 可溯源——每个回答都能追溯到具体的源文档
  • 领域适配——把公司内部文档放入知识库，模型就变成"公司专家"
📚

RAG vs 微调：何时用哪个？RAG 适合"知识更新频繁"和"需要溯源"的场景——随时可以更新文档库。微调适合"改变模型的行为风格"和"教会模型新的任务格式"。很多实际系统两者结合：用微调让模型学会"RAG 的使用方式"，用 RAG 提供实时知识。

5 多 Agent 协作

单个 Agent 能力有限。复杂任务可以拆分给多个专业化的 Agent——每个 Agent 负责一个方面，互相协作完成任务。

# 多 Agent 协作示例：软件开发团队 Product Manager Agent: - 分析用户需求，拆解为具体任务 - 工具：create_task(), prioritize() Developer Agent: - 编写代码，实现功能 - 工具：write_code(), run_tests(), git_commit() Reviewer Agent: - 审查代码质量，提出修改建议 - 工具：read_code(), analyze_complexity(), suggest_fix() Orchestrator（编排者）: - 协调各 Agent 的执行顺序 - 决定何时让哪个 Agent 行动 - 处理 Agent 之间的信息传递 # 工作流程： # 用户提需求 → PM 拆任务 → Developer 写代码 → Reviewer 审查 # → Developer 修改 → Reviewer 通过 → 提交
🏗️

Agent 框架生态：LangChain、LlamaIndex、AutoGen、CrewAI、Dify 等框架提供了构建 Agent 系统的基础设施——工具注册、上下文管理、循环控制、多 Agent 编排。但核心逻辑是通用的：prompt 描述角色→模型决策→执行→反馈→再决策。

6 Agent 的挑战与局限

Agent 系统虽然强大，但目前仍面临一些核心挑战：

🔹 可靠性问题

模型可能调用错误的工具、传入错误的参数、或误解工具返回的结果。Agent 步骤越多，累积出错的概率越高（每步 95% 准确率，10 步后只剩 60%）。

🔹 规划能力有限

当前模型的长期规划能力仍然不足。对于需要 20+ 步的复杂任务，模型经常会"迷失方向"或重复之前的步骤。

🔹 安全风险

Agent 可以执行实际操作（删文件、发邮件、花钱）。如果模型判断失误或被恶意用户诱导，后果可能很严重。需要严格的权限控制和人类审核机制。

🔹 成本与延迟

每次工具调用都意味着一次额外的模型推理（读取结果并决定下一步）。多步 Agent 的延迟和 API 成本都显著高于单轮对话。

# Agent 的可靠性 vs 步骤数： 单步准确率: 95% 3 步成功率: 0.95³ = 85.7% 5 步成功率: 0.95⁵ = 77.4% 10 步成功率: 0.95¹⁰ = 59.9% 20 步成功率: 0.95²⁰ = 35.8% # 这就是为什么复杂 Agent 任务经常"半路跑偏" # 解决方案： # - 把大任务拆成小步骤，减少单次推理的复杂度 # - 每步加入验证/自检机制 # - 关键操作需要人类确认 # - 用更强的模型（准确率更高）
🔮

Agent 的未来：当前的 Agent 还处于"能用但不完全可靠"的阶段。随着模型推理能力的提升（如 o1/o3 的思维链推理）、更好的规划算法（如 MCTS）、以及更可靠的工具接口设计，Agent 的能力正在快速进化。未来的 AI 助手大概率不只是"聊天"，而是能真正"做事"的 Agent 系统。

7 实际案例：你每天都在用的 Agent

你可能没有意识到，很多你日常使用的 AI 产品已经是 Agent 系统：

🌍 真实世界中的 Agent

ChatGPT (with plugins/tools)：搜索网页、执行 Python 代码、生成图片、分析文件——每次你让它"搜一下"或"算一下"，它都在做 Function Calling。

Cursor/Copilot（代码 Agent）：读取项目文件、理解代码库、编写代码、运行测试——你现在用的这个 IDE 就是一个代码 Agent。

Perplexity（搜索 Agent）：把用户问题拆解为多个搜索查询、综合多个网页结果、生成带引用的回答。

Devin/OpenHands（全栈开发 Agent）：自主写代码、调试、提交 PR——尝试完成完整的开发任务。

企业 RPA Agent：自动处理报销、审批、数据录入——按照规则和判断操作各种系统。

8 设计模式：构建可靠的 Agent

# 模式 1: ReAct (Reasoning + Acting) # 每步先"思考"再"行动"，让推理过程透明可追溯 Thought: 用户想知道这个函数的 bug，我需要先看代码 Action: read_file("src/utils.py") Observation: [文件内容...] Thought: 我看到第 42 行有一个 off-by-one 错误 Action: 无需再调工具 Answer: 第 42 行的循环条件应该用 < 而不是 <=... # 模式 2: Plan-and-Execute # 先制定完整计划，再逐步执行 Plan: 1. 搜索竞品分析报告 2. 提取关键数据点 3. 用 Python 画对比图 4. 写总结报告 Execute Step 1: search_web("2024 CRM software market comparison") Execute Step 2: ... # 模式 3: Self-Reflection # 执行后自我检查，发现问题自动修正 Action: write_code(solution) Self-check: 运行测试发现 2 个用例失败 Reflection: 我漏考虑了空列表的情况 Action: write_code(fixed_solution) Self-check: 全部测试通过 ✓
🔑

构建好 Agent 的关键：① 清晰的工具描述（模型只有理解工具才能正确使用）；② 合理的步骤限制（防止无限循环）；③ 错误恢复机制（工具失败时的 fallback）；④ 人类监督（关键操作需确认）；⑤ 日志记录（便于调试和改进）。

9 如何训练一个 Agent？

前面讲的 Agent 能力（Function Calling、多步推理、工具选择）不是从天上掉下来的——它需要专门训练。Agent 的训练方法正在快速发展，这里介绍当前主流的几种思路。

9.1 SFT：用标注好的工具调用示例训练

最基础的方法和第五课学的 SFT 一样：收集大量"问题→思考→工具调用→结果→回答"的示例，当作训练数据。

# Agent SFT 训练数据（一条样本）： { "messages": [ {"role": "user", "content": "北京明天会下雨吗？"}, {"role": "assistant", "content": null, "tool_calls": [{"name": "get_weather", "args": {"city": "北京"}}]}, {"role": "tool", "content": "{\"weather\": \"小雨\", \"temp\": \"12°C\"}"}, {"role": "assistant", "content": "是的，明天北京预报有小雨，气温 12°C，建议带伞出门。"} ] } # 模型从这些示例中学到： # ① 什么时候该调用工具（而不是直接回答） # ② 调用哪个工具、传什么参数 # ③ 怎么基于工具结果生成自然语言回答

这就是 GPT-3.5/4 最初获得 Function Calling 能力的方式。OpenAI 用大量的工具调用对话示例做 SFT，让模型学会了在合适时机输出 JSON 格式的调用指令。

9.2 环境反馈 + RL：让 Agent 在"做事"中学习

SFT 有一个局限：它只能模仿示例中的行为。但 Agent 的核心能力是在复杂环境中自主决策——这靠模仿是不够的，需要让 Agent 真正去尝试、去犯错、从结果中学习。

🎮 Agent RL 的直觉：学打游戏

就像让 AI 学打游戏：你不需要告诉它"在这个画面应该按左键"——你只需要让它不停地打，然后告诉它"这局赢了（+1 分）"或"这局输了（-1 分）"。几百万局之后，它自己就学会了最优策略。

Agent 训练的逻辑类似：

① 给 Agent 一个任务（如"帮我查机票并预订最便宜的"）
② 让它在模拟环境中自由操作（调 API、填表单、点按钮……）
③ 任务完成了 → 奖励；做错了或超时 → 惩罚
④ 用强化学习（如 PPO）更新模型参数

# Agent RL 训练循环（伪代码）： for episode in range(训练轮数): task = sample_task() # 随机抽一个任务 env = create_environment(task) # 创建模拟环境 for step in range(max_steps): observation = env.get_state() # 当前状态 action = agent.decide(observation) # Agent 决策 result, reward, done = env.execute(action) # 执行并获得反馈 if done: break # 根据整个 episode 的奖励更新 Agent agent.update(trajectory, total_reward) # 关键：奖励信号来自环境（任务是否完成）而不是人类标注

典型的 Agent 训练环境：

  • WebArena / VisualWebArena — 在真实网页上操作（搜索、购物、填表）
  • SWE-bench — 在真实 GitHub 仓库中修 bug、写代码
  • OSWorld — 在完整操作系统中执行任务（打开应用、编辑文件）
  • API-Bank — 调用各种模拟 API 完成多步任务

9.3 轨迹级 RLHF / DPO：从偏好中学决策

第五课学的 RLHF 和 DPO 也可以用来训练 Agent——只不过"偏好对"从单轮回答变成了完整的操作轨迹（trajectory）：

# 单轮 DPO（第五课）：比较两个"回答" 好回答: "巴黎是法国的首都，位于塞纳河畔。" 差回答: "法国的首都好像是里昂吧。" # Agent DPO：比较两条"完整操作轨迹" 好轨迹: search("北京到杭州高铁") → 选最早班次 → book(G7501) → 完成 ✓ 差轨迹: search("北京杭州") → 点进无关链接 → search("火车票") → 超时 ✗ # 训练目标一样：让模型更倾向于产生"好轨迹"的行为模式

这种方法的优势是不需要复杂的环境模拟器——只要能收集到成功和失败的操作记录，就可以用 DPO 来训练。很多公司用线上真实的 Agent 操作日志（成功/失败）作为训练数据。

9.4 过程奖励：每一步都给反馈

Agent 任务通常有很多步。如果只在最后告诉模型"成功/失败"，模型很难知道到底哪一步做对了、哪一步做错了——这叫"信用分配问题"（credit assignment problem）。

过程奖励模型（Process Reward Model, PRM）的解决方案是：不只给最终结果打分，而是给每一步都打分。

# 结果奖励 vs 过程奖励： # 结果奖励（Outcome RM）： Step 1: search("航班") → ? Step 2: filter(最便宜) → ? Step 3: book(错误的航班) → ? Step 4: 任务失败 → -1 ← 只有最后一步有反馈 # 模型：到底哪一步错了？？？ # 过程奖励（Process RM）： Step 1: search("航班") → +0.8 ✓ 搜索词合理 Step 2: filter(最便宜) → +0.9 ✓ 筛选逻辑正确 Step 3: book(错误的航班) → -0.7 ✗ 选错了！这里出问题了 Step 4: 任务失败 → -1.0 # 模型：哦，Step 3 的选择逻辑有问题，我需要改进这一步

过程奖励让模型能更快、更精准地学习。OpenAI 的 o1/o3 系列模型就大量使用了过程奖励来训练推理和多步决策能力。

🧭

Agent 训练的当前趋势：实践中往往是多种方法混合使用——先用 SFT 让模型学会基本的工具调用格式，再用 RL 或 DPO 在具体任务环境中优化决策质量，最后用过程奖励精调多步推理。这和聊天模型的训练路径（预训练→SFT→RLHF）是一脉相承的，只不过"数据"从对话变成了操作轨迹，"评价标准"从回答质量变成了任务完成率。

10 检验你的理解

Q1: Function Calling 的实现原理是什么？

✅ 正确！Function Calling 不需要修改模型架构。模型还是在做 Next-Token Prediction，只不过它被训练为"在合适的时候，输出格式化的工具调用 JSON"。外部系统解析这个 JSON，执行工具，再把结果作为文本反馈给模型。
❌ 模型架构不需要任何改变。Function Calling 本质上是训练模型学会"输出特定格式的文本"——这些文本恰好是 JSON 格式的工具调用指令。系统负责解析和执行。

Q2: RAG 相比直接让模型回答的主要优势是？

✅ 正确！RAG 让模型的回答基于真实检索到的文档，而不是从参数记忆中"回忆"。这减少了幻觉，而且只要更新文档库就能更新知识——不需要重新训练模型。还能追溯每个回答的信息来源。
❌ RAG 实际上比纯模型回答稍慢（多了检索步骤）。它的核心优势是：基于真实文档减少幻觉、知识可更新、可溯源。

Q3: 为什么 Agent 的可靠性随步骤数增加而下降？

✅ 正确！如果每步有 5% 的出错概率（调错工具、传错参数、误解结果），那连续 10 步全对的概率只有 0.95¹⁰ ≈ 60%。这是复合概率的必然规律。解决方法：减少步骤数、提高单步准确率、加入自检和回退机制。
❌ 核心原因是概率的乘法：每步 95% 准确 → 10 步后只剩 60%。错误会随步骤数指数级累积。这和上下文长度或执行速度无关。

Q4: 以下哪个不是 Agent 安全性的核心关注点？

✅ 正确！Agent 安全的核心关注是：① 不被诱导做坏事（注入攻击）；② 不因误判做不可逆操作（权限控制）；③ 操作在用户授权范围内（最小权限原则）。回答是否有趣是体验问题，不是安全问题。
❌ Agent 的安全问题比聊天机器人严重得多——因为它能执行真实操作。误删文件、发错邮件、被注入攻击利用都是实际威胁。"不够幽默"只是体验问题，不是安全关注点。

11 编程练习：构建一个迷你 Agent

本课的编程练习将让你从零实现一个能调用工具的迷你 Agent 系统。你会看到 Agent Loop 的完整运转——从解析用户意图，到选择工具，到执行并整合结果。

🛠️ 你的任务：构建迷你 Agent

在配套的 exercise.py 中，按顺序完成 5 个任务：

任务 1：parse_tool_call() — 解析模型输出的工具调用
从模型的文本输出中提取工具名称和参数——Agent 的"耳朵"。

任务 2：execute_tool() — 执行工具并返回结果
根据工具名和参数调用对应的函数——Agent 的"手"。

任务 3：should_use_tool() — 决策是否需要工具
根据用户问题判断是直接回答还是调用工具——Agent 的"大脑"。

任务 4：format_context() — 构建工具结果的上下文
把工具返回的结果格式化为模型能理解的 prompt——Agent 的"记忆"。

任务 5：agent_loop() — 完整的 Agent 循环
把所有组件串起来：接收问题→决策→调用工具→整合结果→回答。完整的 Agent！
