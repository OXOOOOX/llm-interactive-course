0 为什么推理优化重要？

训练是一次性的投入，但推理是持续不断的成本。当 ChatGPT 每天处理数亿次请求时，推理成本远超训练。一个未优化的 175B 参数模型，生成一个 token 就需要数百毫秒——用户等不起。

# 推理的两大核心指标： 延迟（Latency）：生成一个 token 需要多少毫秒？ → 决定用户体验（等待 vs 流畅对话） 吞吐量（Throughput）：每秒能生成多少 token？ → 决定服务多少用户的能力和成本 # 两者往往需要权衡： # 大 batch → 吞吐量高但单个请求延迟增大 # 小 batch → 延迟低但 GPU 利用率不高

1 自回归生成的天然瓶颈

回忆第三课：大模型生成文本是逐 token 生成的——每次只生成一个 token，然后把它加入输入序列，再预测下一个。这意味着生成 100 个 token 需要跑 100 次前向传播。

# 自回归生成的流程： 输入: "今天天气" Step 1: 模型处理 ["今","天","天","气"] → 预测 "真" → ~30ms Step 2: 模型处理 ["今","天","天","气","真"] → 预测 "好" → ~30ms Step 3: 模型处理 ["今","天","天","气","真","好"] → 预测 "，" → ~30ms ... # 生成 200 个 token ≈ 200 × 30ms = 6 秒 # 用户要等 6 秒才能看到完整回答——不可接受！ # 而且注意：每一步都要重新处理所有之前的 token # Step 3 又在重复计算 "今天天气真" 这些已经算过的东西 # 这就是巨大的浪费！→ KV Cache 来解决

大模型推理还有一个独特的特点：内存瓶颈（Memory-Bound）而非计算瓶颈。

💾

为什么是内存瓶颈？生成每个 token 时，模型只做一次矩阵-向量乘法（不是矩阵-矩阵）。对于 175B 参数的模型，每次前向需要从显存读取 350GB 的参数，但只做很少量的计算。GPU 的显存带宽（~2TB/s）成了瓶颈，而不是算力（~300 TFLOPS）。这就像你有一台超快的 CPU，但硬盘读取速度跟不上——计算单元大部分时间在"等数据"。

2 KV Cache：不做重复计算

KV Cache 是大模型推理中最基本也最重要的优化。核心思想：把已经算过的 Key 和 Value 缓存起来，下次直接复用。

回忆 Self-Attention 的计算：每个 token 需要和所有之前的 token 计算注意力。如果不缓存，每生成一个新 token，都要重新计算前面所有 token 的 K 和 V——这是巨大的浪费。

📦 KV Cache 工作原理

缓存的 K/V（绿色）不需要重新计算，每步只需计算新 token（橙色）的 K/V：

Step 1
今 天 天 气 → 真
计算全部 4 个 K/V
Step 2
今 天 天 气 真 → 好
只算 1 个新 K/V ✓
Step 3
今 天 天 气 真 好 → ，
只算 1 个新 K/V ✓
Step N
... N-1 个缓存 新 → ?
始终只算 1 个 ✓
# 没有 KV Cache：每步计算量 ∝ 序列长度（越来越慢） Step 1: 处理 4 个 token Step 2: 处理 5 个 token # 包括重新算前 4 个的 K/V Step 3: 处理 6 个 token # 包括重新算前 5 个的 K/V ... Step N: 处理 N+3 个 token # 有 KV Cache：每步只处理 1 个新 token（恒定速度） Step 1: 处理 4 个 token → 缓存 4 组 K/V Step 2: 处理 1 个新 token → 缓存追加 1 组 K/V Step 3: 处理 1 个新 token → 缓存追加 1 组 K/V ... Step N: 处理 1 个新 token → 注意力计算用缓存中的所有 K/V # 加速比：对于生成 1000 个 token，节省约 500× 计算量

KV Cache 的代价：需要额外显存来存储缓存。对于 LLaMA-70B，每个 token 的 KV Cache 占约 1.6MB。处理一个 4096 长度的序列就需要 ~6.5GB。当同时服务多个用户时，KV Cache 的显存消耗可能比模型参数本身还大！

⚡

Prefill vs Decode 两阶段：推理分为两个阶段。Prefill（预填充）：处理用户的输入（prompt），一次性计算所有输入 token 的 K/V，这一步是计算密集型（Compute-Bound），可以高效并行。Decode（解码）：逐个生成输出 token，每步只处理一个 token，是内存密集型（Memory-Bound）。这两个阶段的特性完全不同，很多优化针对其中一个。

3 量化：用更少的位数表示参数

量化（Quantization）是另一个关键优化：把模型参数从高精度（FP16，16位）压缩为低精度（INT8 或 INT4，8位或4位）。参数占用的空间减半甚至减至四分之一——意味着显存需求大幅降低，读取速度更快，推理更快。

INT4 量化让 70B 模型能跑在单张 40GB 的 A100 上（原本需要 3-4 张）！

# 量化的基本原理： # FP16 的值域范围很大：约 -65504 到 +65504 # 但模型的参数通常集中在一个小范围内（如 -1.0 到 +1.0） # INT8 量化：把 [-1.0, 1.0] 映射到 [-128, 127] scale = (max_val - min_val) / 255 quantized = round((float_val - min_val) / scale) # 例：float_val = 0.35, 范围 [-1, 1] scale = 2.0 / 255 = 0.00784 quantized = round((0.35 - (-1.0)) / 0.00784) = round(172.2) = 172 # 还原： dequantized = 172 × 0.00784 + (-1.0) = 0.3485 # 有微小误差 # 关键洞见：这点误差对模型输出的影响微乎其微 # 神经网络对参数的微小扰动天然鲁棒

量化方法的演进：

  • PTQ（Post-Training Quantization）：训练后直接量化，不需要额外训练。简单快速。
  • GPTQ：更精细的逐层量化，通过最小化量化误差来选择最优的量化参数。
  • AWQ（Activation-Aware）：不平等对待所有参数——对激活值影响大的参数保留更高精度。
  • GGUF（llama.cpp）：针对 CPU 推理优化的混合精度格式，让大模型能在普通电脑上运行。
🎯

量化的惊人发现：研究表明，4-bit 量化后的模型在大多数任务上几乎无损——性能下降通常不超过 1-2%。这意味着你可以用四分之一的资源获得几乎同等的效果。这也是为什么像 llama.cpp 这样的项目能让 7B 模型在 MacBook 上流畅运行——INT4 量化后只需要约 4GB 内存。

4 投机采样：用小模型加速大模型

投机采样（Speculative Decoding）是一个巧妙的加速技巧：用一个小而快的模型来"猜测"大模型可能生成什么，然后让大模型一次性验证。如果猜对了——跳过很多步；猜错了——回退到猜错的位置。

# 投机采样的流程： # 假设有一个 7B 小模型（快 10×）和一个 70B 大模型（慢但准确） # 1. 小模型快速生成 K 个 token（如 K=5）： draft = small_model.generate(5 tokens) # → ["今", "天", "天", "气", "真"] # 2. 大模型一次性验证这 5 个 token（并行！）： verified = large_model.verify(draft) # 对于每个位置，检查大模型是否同意小模型的选择 # 假设前 4 个都对，第 5 个大模型想生成"不"而非"真"： # → 接受 ["今", "天", "天", "气"]，拒绝 "真"，替换为 "不" # 3. 本轮结果：一次大模型前向传播生成了 5 个 token！ # 而不是通常的 1 个——加速了 ~5× # 关键性质：输出和直接用大模型生成完全一致 # 这不是近似！是数学上等价的精确加速
🎲

为什么这能保证结果一致？投机采样用了一个精妙的概率论技巧（rejection sampling）：对于小模型和大模型一致的 token，直接接受；对于不一致的，按照两者概率的差值做采样。最终的 token 序列的概率分布和纯粹用大模型生成的完全一样。这就像让助手先写草稿，老板快速审阅——如果草稿好就直接用，不好就老板改，最终产出的质量和老板亲自写一样。

投机采样的加速倍数取决于小模型和大模型的"一致率"。对于同系列的模型（如 LLaMA-7B + LLaMA-70B），一致率通常在 70-85%，实际加速约 2-3×。

5 批处理与调度：同时服务更多人

在生产环境中，服务器需要同时处理成百上千个用户的请求。如何高效地把这些请求"打包"在一起处理，是吞吐量优化的关键。

🔹 Continuous Batching（连续批处理）

传统的 batching 会等一批请求全部完成再处理下一批——短请求要等长请求。Continuous Batching 允许已完成的请求立即退出、新请求立即加入，就像餐厅翻台——吃完的立即离开，不用等全桌人都吃完。

# 传统 Static Batching： Batch 1: [请求A(10 token), 请求B(100 token), 请求C(50 token)] # 请求A 生成 10 个 token 就结束了，但要等 B 生成完 100 个才能开始 Batch 2 # A 和 C 的位置在后面 90/50 步中被浪费了 # Continuous Batching： Step 1-10: [A, B, C] # 三个都在生成 Step 11: [D, B, C] # A 完成，新请求 D 立即加入！ Step 12-50: [D, B, E] # C 完成，E 加入 ... # GPU 始终满负荷运转，不浪费任何位置

🔹 PagedAttention（vLLM）

KV Cache 的显存管理是一个难题：不同请求的序列长度不同，传统方法需要预分配最大长度的显存——浪费巨大。vLLM 的 PagedAttention 借鉴了操作系统的虚拟内存管理：把 KV Cache 分成固定大小的"页"，按需分配，避免碎片化。

# PagedAttention 的类比： # 传统方式 = 预订固定长度的停车位 # 不管你车多大，都给你 2048 格长的停车位 → 大量空间浪费 # PagedAttention = 立体停车场按需分配 # 小车停 2 格，大车停 5 格，灵活分配 → 利用率大幅提高 # 实测效果：vLLM 相比 HuggingFace 原生推理 # 吞吐量提升 2-4×，显存浪费减少 60-80%
🏗️

推理框架生态：目前主流的推理框架包括 vLLM（PagedAttention + Continuous Batching）、TensorRT-LLM（NVIDIA 官方优化）、SGLang（编译优化）、llama.cpp（CPU/Metal推理）。它们各有侧重，但核心都在解决同一个问题：如何在有限的 GPU 资源上最大化推理效率。

6 采样策略：控制生成的多样性

模型输出的是一个概率分布——但怎么从分布中选择最终的 token？不同的选择策略会产生截然不同的文本风格：

# 假设模型对下一个 token 的概率分布（Top-5）： # "好" → 0.35, "棒" → 0.25, "美" → 0.15, "妙" → 0.10, "佳" → 0.05 Greedy（贪心）：始终选概率最高的 → 总是选 "好"（确定性，但可能重复单调） Temperature（温度）：控制概率的"尖锐度" T=0.1 → [0.85, 0.12, 0.02, 0.01, 0.00] # 几乎确定选"好" T=1.0 → [0.35, 0.25, 0.15, 0.10, 0.05] # 原始分布 T=2.0 → [0.28, 0.24, 0.20, 0.16, 0.12] # 更均匀，更随机 Top-K：只从概率最高的 K 个中采样 K=3 → 只从 "好/棒/美" 中选（排除低概率的奇怪选项） Top-P (Nucleus)：只从累积概率达到 P 的最小集合中采样 P=0.8 → "好"(0.35) + "棒"(0.25) + "美"(0.15) + "妙"(0.10) = 0.85 > 0.8 → 从 "好/棒/美/妙" 这 4 个中采样 # 实际使用中通常组合多种策略： # temperature=0.7, top_p=0.9 是一个常见的平衡设置
策略适用场景效果
T=0 (Greedy)代码、数学、事实问答确定性、一致性
T=0.3-0.7日常对话、写作辅助平衡创造性与准确性
T=1.0+创意写作、头脑风暴多样性强、可能偏离主题

7 长上下文的挑战与优化

现代大模型的上下文窗口越来越长（GPT-4 128K、Claude 200K、Gemini 1M+）。但更长的上下文意味着更大的 KV Cache 和更慢的注意力计算（Attention 复杂度是 O(n²)）。

# 上下文长度 vs 资源需求（以 LLaMA-70B 为例）： 上下文 4K: KV Cache ≈ 6.5 GB Attention 计算 ≈ 1× 上下文 32K: KV Cache ≈ 52 GB Attention 计算 ≈ 64× 上下文 128K: KV Cache ≈ 208 GB Attention 计算 ≈ 1024× # KV Cache 随长度线性增长 # Attention 计算随长度平方增长（每个 token 要和所有前面的 token 算注意力）

关键优化技术：

① Flash Attention——重新排列注意力的计算顺序，让它对 GPU 内存层级更友好（减少 HBM 读写次数）。不改变计算结果，纯粹的工程优化，速度提升 2-4×，显存节省 5-20×。

② GQA（Grouped Query Attention）——让多个 Query Head 共享同一组 Key/Value Head。LLaMA-2 70B 用 8 组 KV 服务 64 个 Query Head，KV Cache 大小降低 8×。

③ Sliding Window Attention——每个 token 只看最近的 N 个 token（如 4096 个），而不是整个上下文。Mistral 用此方法支持超长序列而不爆显存。

🔭

Flash Attention 的直觉：想象你要计算 1000×1000 的矩阵乘法。如果一次性把整个矩阵加载到高速缓存——放不下。Flash Attention 的做法是"分块计算"：每次只加载一小块数据到 SRAM（极快但极小），在 SRAM 里算完再写回 HBM。就像把一本巨大的字典拆成小册子，每次只查一册。减少了 GPU 显存（HBM）的读写次数，获得了巨大的加速。

9 检验你的理解

Q1: KV Cache 为什么能加速推理？

✅ 正确！在自回归生成中，每一步都需要和所有历史 token 计算注意力。如果不缓存，每步都要重新计算前面所有 token 的 K 和 V。有了 KV Cache，只需计算新 token 的 K/V，然后和缓存中的做注意力计算即可。
❌ KV Cache 不涉及压缩或跳过 token。它的核心是"记住已算过的"——每步只算新增的一个 token 的 K/V，历史的直接从缓存读取。

Q2: INT4 量化把 70B 模型从 140GB 压缩到约 35GB，主要原因是？

✅ 正确！量化不删除任何参数，只是用更少的位数来表示同样的值。16位→4位，存储量直接变为 1/4。这会引入微小的精度误差，但神经网络对此非常鲁棒——大多数任务几乎无损。
❌ 量化不是剪枝（不删除参数）也不是通用压缩。它是把每个参数的数值精度降低——从 16 位浮点数变为 4 位整数。参数数量不变，但每个参数占用的空间减少了 4 倍。

Q3: 投机采样（Speculative Decoding）为什么能保证输出质量不下降？

✅ 正确！投机采样的精妙之处在于：小模型生成候选，但大模型有最终决定权。通过 rejection sampling（拒绝采样），不一致的 token 会被拒绝并重新采样，保证最终输出的概率分布与纯大模型生成完全一致。加速但不牺牲质量。
❌ 关键在于大模型"验证"了每个 token。小模型只是提供"草稿"，大模型做最终裁判——同意则接受，不同意则按大模型的分布重新采样。数学上保证了最终结果和直接用大模型一样。

Q4: Temperature = 0 时，模型的生成行为是？

✅ 正确！Temperature → 0 时，概率分布变成"one-hot"——最高概率的 token 趋向 100%，其他趋向 0%。效果等同于贪心解码，每次运行结果完全一致。适合需要确定性的场景（代码、数学），但可能缺乏多样性。
❌ Temperature 控制概率分布的"尖锐度"。T→0 让分布极度集中在最高概率的 token 上（贪心）。T→∞ 才是完全均匀/随机。T=1 是原始分布。
